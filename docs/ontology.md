# Ontology

The ontology is the shared vocabulary used by the Mapper, the graph queries, and
the Client's type checks. It has a small hand-written upper layer, a unit registry
that is also emitted as RDF, and a curated seed domain layer of 179 concepts
(206 in the local app fallback). The committed artifact `data/out/ontology.ttl`
is rebuilt from that seed layer. The LLM generation path can
extend the source layer when a provider key and cache are available.

## 1. Namespaces and IRIs

Defined in `src/agent_bazaar/ontology/ns.py:8-22`:

| Prefix | IRI | Used for |
| --- | --- | --- |
| `ab` | `https://agent-bazaar.local/ontology#` | Classes, properties, concepts, mappings, capabilities, providers, and unit *families* |
| `tool` | `https://agent-bazaar.local/tool/` | Tool instances (`tool:<tool_id>`) |
| `unit` | `https://agent-bazaar.local/unit#` | Unit instances (`unit:Celsius`) |
| `owl`, `rdf`, `rdfs`, `sh`, `skos`, `xsd` | standard W3C namespaces | Typing, labels, aliases, SHACL, literals |

The ontology document itself is `https://agent-bazaar.local/ontology` (no `#`).
Concept IRIs use the local name, for example
`https://agent-bazaar.local/ontology#Temperature`. `tool_iri()` and `unit_iri()`
are the only constructors used by the code (`ns.py:25-30`).

## 2. Upper ontology

`src/agent_bazaar/ontology/upper.ttl` declares 12 upper classes and the
properties the layers share. `Tool` is a `Service`; `Input` and `Output` are
`Concept`s. `Mapping`, `Unit`, `UnitFamily`, `Claim`, `Evidence`, `Provider`, and
`Capability` are separate classes.

| Class | Meaning |
| --- | --- |
| `ab:Service` | General service |
| `ab:Tool` | Callable third-party service listed in the bazaar |
| `ab:Provider` | Organisation that provides a tool |
| `ab:Capability` | What a tool can do |
| `ab:Concept` | Typed domain concept; domain concepts are `owl:Class` and `ab:Concept` |
| `ab:Input`, `ab:Output` | Subclasses of `Concept` used for documentation and shapes |
| `ab:Claim`, `ab:Evidence` | Provider statement and supporting material |
| `ab:Mapping` | One field-to-concept record with provenance |
| `ab:UnitFamily`, `ab:Unit` | Unit classification and concrete units |

Object properties:

| Property | Domain -> range |
| --- | --- |
| `ab:hasCapability` | Tool -> Capability |
| `ab:hasInput` | Tool -> Concept |
| `ab:hasOutput` | Tool -> Concept |
| `ab:makesClaim` | Tool -> Claim |
| `ab:supportedBy` | Claim -> Evidence |
| `ab:providedBy` | Tool -> Provider |
| `ab:mapsTo` | Mapping -> Concept |
| `ab:hasFieldMapping` | Tool -> Mapping |
| `ab:tool` | Mapping -> Tool |
| `ab:unitOfFamily` | Unit -> UnitFamily |
| `ab:unitFamily` | Concept -> UnitFamily |
| `ab:defaultUnit` | Concept -> Unit |
| `ab:unit` | Mapping -> Unit |

Data and annotation properties include `ab:hasTrust` (decimal 0-1), `ab:toolId`,
`ab:name`, `ab:description`, `ab:source`, `ab:version`, `ab:providerId`,
`ab:homepage`, `ab:claimId`, `ab:claimText`, `ab:evidenceId`, `ab:content`,
`ab:hasDataType`, `ab:unitBearing`, `ab:unitSymbol`, `ab:familyCode`,
`ab:fieldPath`, `ab:direction`, `ab:confidence`, `ab:reason`, `ab:status`,
`ab:attempts`, `ab:recordedAt`, `ab:recordedBy`, and `ab:note`
(`upper.ttl:100-205`).

`ab:hasDataType` is one of `float`, `integer`, `string`, `boolean`, `date`,
`datetime`, `object`, `array`. These are string tags, not XSD datatypes.

## 3. Unit families and conversions

`src/agent_bazaar/ontology/units.py` is the single source of truth. The graph
triples are generated by `units_graph()` (`units.py:186`), so code and graph
cannot disagree.

| Family | Canonical | Units (local names) |
| --- | --- | --- |
| `TemperatureUnit` | Celsius | Celsius, Fahrenheit, Kelvin |
| `LengthUnit` | Metre | Metre, Kilometre, Centimetre, Mile, Foot |
| `DurationUnit` | Second | Second, Millisecond, Minute, Hour, Day |
| `SpeedUnit` | MetrePerSecond | MetrePerSecond, KilometrePerHour, MilePerHour, Knot |
| `MassUnit` | Kilogram | Kilogram, Gram, Pound |
| `PressureUnit` | Hectopascal | Hectopascal, Pascal, Kilopascal, Millibar |
| `PrecipitationUnit` | Millimetre | Millimetre, Inch |
| `PercentageUnit` | Percent | Percent |
| `AngleUnit` | Degree | Degree, Radian |
| `AreaUnit` | SquareKilometre | SquareKilometre, SquareMetre, SquareMile |
| `CountUnit` | Count | Count |
| `CurrencyUnit` | USD | USD, EUR, GBP, PKR, JPY (not convertible) |

Each unit has a symbol (`C`, `m`, `km/h`, `%`, ...). Currency units are marked
`convertible=False` because a rate is needed; `convert()` raises `ValueError`
for them (`units.py:161-183`).

In the emitted graph a unit instance is `unit:<LocalName>` but a family is
`ab:<FamilyName>`, because `units_graph()` builds families with `AB[family_name]`
and units with `unit_iri(local_name)` (`units.py:186-199`). A concept's
`ab:unitFamily` points at `ab:TemperatureUnit` and its `ab:defaultUnit` at
`unit:Celsius`.

Conversion is affine around the canonical unit:

```text
canonical = (value + offset) * factor
value     = canonical / factor - offset
```

Examples: `68 F` -> `20 C`; `0 C` -> `273.15 K`; `1 km` -> `1000 m`;
`1 mi` -> `1.609344 km`. A conversion between different families raises
`ValueError`. `compatible_units(a, b)` is true only when both units exist and
share a family (`units.py:157`).

Helpers: `unit_def(name_or_iri)`, `family_of()`, `units_in_family()`,
`compatible_units()`, `convert()`. Names may be local names or IRIs; the `#`
suffix is stripped.

## 4. Domain concepts (60)

The seed is `SEED_CONCEPTS` in `src/agent_bazaar/ontology/domain.py:61`. Each
concept has a local name, label, data type, optional parents, optional unit
family/default unit, aliases, and definition. `merge_concepts()` removes
duplicates by local name, label, or alias and keeps the richer record
(`domain.py:153`).

### Geo (12)

`Position`, `Latitude`, `Longitude`, `Address`, `City`, `Region`, `PostalCode`,
`CountryName`, `CountryCode`, `PlaceName`, `Timezone`, `Elevation`.

Unit-bearing: `Latitude`, `Longitude`, `WindDirection` (weather) and
`Elevation` use angle/length families. `Position` is an object; addresses, place
names, and codes are strings.

### Weather (16)

`Temperature`, `FeelsLikeTemperature`, `DewPoint`, `WindSpeed`,
`WindDirection`, `Humidity`, `Precipitation`, `Pressure`, `CloudCover`,
`WeatherCondition`, `WeatherCode`, `UVIndex`, `Visibility`, `SunriseTime`,
`SunsetTime`, `Forecast`.

`FeelsLikeTemperature` is a child of `Temperature`. Temperature concepts use
`TemperatureUnit`; speed uses `SpeedUnit`; direction uses `AngleUnit`; humidity
and cloud cover use `PercentageUnit`; precipitation uses
`PrecipitationUnit`; pressure uses `PressureUnit`.

### Currency (6)

`Currency`, `CurrencyCode`, `ExchangeRate`, `MoneyAmount`, `BaseCurrency`,
`QuoteCurrency`.

Note that the seed declares `CurrencyCode` under `CountryCode`; this is the
current model even though the two domains are different.

### General reference (26)

`Country`, `Holiday`, `HolidayName`, `HolidayDate`, `Capital`, `Language`,
`Population`, `AreaSize`, `FlagUrl`, `Distance`, `Duration`, `Speed`, `Mass`,
`Percentage`, `ISODate`, `DateTime`, `Name`, `Description`, `Identifier`,
`Count`, `Rank`, `Rating`, `BooleanFlag`, `Url`, `Email`, `PhoneNumber`.

Unit-bearing examples: `Population` and `Count` (`CountUnit`), `AreaSize`
(`AreaUnit`), `Distance` (`LengthUnit`), `Duration` (`DurationUnit`), `Speed`
(`SpeedUnit`), `Mass` (`MassUnit`), `Percentage` (`PercentageUnit`).

Aliases are SKOS `altLabel`s and are used by retrieval and heuristic matching,
for example `temp_c`, `lat`, `lon`, `zip`, `iso_code`, `timestamp`.

## 5. SHACL shapes and deterministic rule checks

`src/agent_bazaar/ontology/shapes.ttl` defines node shapes. `validator.py`
runs pySHACL and then adds rule checks that are cheaper or clearer outside
SHACL.

| Shape | Focus | Main constraints |
| --- | --- | --- |
| `ab:ConceptShape` | `ab:Concept` | Exactly one label; exactly one data type from the allowed list; at least one parent; at most one boolean `unitBearing`; at most one IRI `unitFamily`; aliases are strings |
| `ab:MappingShape` | `ab:Mapping` | Exactly one `fieldPath`, `tool`, `mapsTo`, and `direction` (`input`/`output`); optional decimal confidence 0-1; at most one unit; at most one integer attempts |
| `ab:ToolShape` | `ab:Tool` | Exactly one name and provider; at least one capability; at least one typed output concept; inputs typed; optional trust 0-1 |
| `ab:ClaimShape` | `ab:Claim` | Exactly one `claimText`; at least one `source` |
| `ab:EvidenceShape` | `ab:Evidence` | At least one `source` |
| `ab:ProviderShape` | `ab:Provider` | Exactly one `providerId` |
| `ab:UnitShape` | `ab:Unit` | Exactly one symbol and unit family |
| `ab:UnitFamilyShape` | `ab:UnitFamily` | Exactly one family code |

`ToolShape` is the reason a tool with no mapped output fields cannot be written:
`ab:hasOutput` has `sh:minCount 1` (`shapes.ttl:126-132`).

Deterministic checks in `src/agent_bazaar/ontology/validator.py`:

1. **Duplicate labels** across concepts (`DUPLICATE_LABEL_QUERY`, lines 19-24).
2. **Duplicate aliases** across concepts (`DUPLICATE_ALIAS_QUERY`, lines 26-31).
3. **Unit-bearing concept declares a unit family** (`unit_family_declaration_violations`,
   lines 91-106).
4. **Mapping unit compatibility**: a unit-bearing concept requires a unit and a
   declared family; if a unit is present and the concept has a family, the unit
   must belong to that family (`mapping_unit_violations`, lines 109-137). This
   graph check does not reject a unit on a non-unit-bearing concept; the Mapper's
   `check_mapping()` does that before a write.

`validate_graph()` merges the SHACL results with these checks and sets
`conforms` to `False` if either source reports a violation
(`validator.py:148-166`). `inference` defaults to `none`; the graph store uses
the installed shapes file. `check_data_node()` builds a small subgraph around one
node for targeted checks (`validator.py:169`).

Performance note: the shapes use `sh:targetClass`, not expensive SPARQL targets,
and the cross-node checks are single grouped queries or loops over the relevant
nodes. On the committed seed graph (7,196 triples) a full `KgStore.validate()`
measures roughly 1.3-2.0 s in the current checkout, of which about 1.5-1.7 s is
pySHACL and about 0.2-0.3 s is the deterministic rule checks. An earlier
development run on a different machine recorded about 0.37 s for the same
validation, against roughly 1.7-3.3 s for the earlier SPARQL-target
formulation; that comparison is project history and cannot be re-measured here
because the SPARQL-target shapes are no longer in the repository. Reproduce the
current figure with:

```powershell
python -c "import time; from agent_bazaar.kg.store import KgStore; s=KgStore.build_default(); t=time.perf_counter(); r=s.validate(); print(f'{time.perf_counter()-t:.3f}s conforms={r.conforms}')"
```

These are indicative local measurements, not a controlled benchmark.

## 6. Generation pipeline

The generator is `src/agent_bazaar/ontology/generator.py`; the CLI is
`scripts/build_ontology.py`.

1. **Inventory.** `field_inventory()` ingests every `*.json` spec in the corpus,
   skips `manifest.json`, and collects field name, type, description, and tool id.
2. **Seed protection.** `_prepared_seed()` removes aliases that collide with
   another concept's local name or label.
3. **Uncovered fields.** `uncovered_field_samples()` keeps fields whose tokens do
   not intersect the seed vocabulary.
4. **Fallback.** If the client is `None`, `use_llm` is false, the provider is
   `offline`, or there are no uncovered fields, `_seed_layer()` validates and
   returns the 179 concepts with `source="seed"` (`generator.py:385-430`).
5. **LLM batches.** Uncovered fields are chunked (default 40). The system prompt
   lists upper classes, properties, valid data types, and unit families/units.
   The model returns a `ProposalBatch`.
6. **Sanitize.** Unknown unit families or units, and units outside the declared
   family, are dropped or cleared (`sanitize_proposals`, lines 124-144).
7. **Merge and validate.** Proposals become domain concepts with PascalCase local
   names, are merged with the seed, and are validated against upper + units +
   domain.
8. **Repair.** Violations are returned to the model for at most
   `max_repair_rounds` (default 2) complete corrected batches. Every round is
   logged to `data/out/logs/ontology_violations.jsonl`. If validation still
   fails, `OntologyGenerationError` is raised.
9. **Artifact.** `build_ontology.py` writes `ontology.ttl` (upper + units +
   domain), `domain.ttl`, and `data/out/logs/ontology_build.json` with source,
   concept count, violation counts, repair rounds, batch counts, and inventory
   stats.

Every LLM call is cached by the client, so a generated layer can be reproduced
from `data/cache/llm`. With `--offline`, the committed seed is used and no network
call is made. The committed `data/out/ontology.ttl` is an offline seed build; it
does not claim to be an LLM-generated layer.

## 7. How to extend

1. Add a concept in `domain.py` with `_concept(...)`:
   - unique `local_name` and `label`;
   - a valid `data_type`;
   - parents that already exist (`Concept` or a specific concept);
   - if unit-bearing, a valid `unit_family` and `default_unit`;
   - aliases that do not duplicate another concept's label or alias.
2. If a new unit is needed, add a `UnitDef` to `UNIT_FAMILIES` in `units.py` with
   symbol, family, factor, offset, and convertibility. Do not create unit triples
   by hand; `units_graph()` emits them.
3. Rebuild offline and run the ontology/graph tests:

```powershell
python scripts/build_ontology.py --offline
python -m pytest tests/test_ontology_generator.py tests/test_kg_store.py tests/test_kg_queries.py
```

4. For the LLM path, set a provider key and run without `--offline`; review the
   reported source, violations, and top-level concepts before committing an
   artifact. Use `--limit-specs` for a quick review run.
5. Only change `shapes.ttl` when a new invariant is required. Add a deterministic
   check in `validator.py` if the condition is cross-node or cheaper as a grouped
   query. Revalidate the graph after any shape change.
6. Do not edit `data/out/ontology.ttl` by hand. It is generated; `domain.ttl` and
   the build summary are regenerated with it.

## 8. Name mapping in the application layer

The Client/Provider/Interface application carries a small local fallback ontology
(`app/data/ontology.json`) whose names differ from the ones above.
`app/integration/canonical.py` is the single translation point between the two
vocabularies, so no other module has to hard-code an alias.

| Local app name | Canonical name |
| --- | --- |
| `LocationName` | `PlaceName` |
| `CityName` | `City` |
| `Coordinates` | `Position` |
| `Money` | `MoneyAmount` |
| `Text` | `Description` |
| `Number` | `Count` |
| `DateTimeISO` | `DateTime` |

The unit names are mapped the same way: `C` to `Celsius`, `F` to `Fahrenheit`,
`K` to `Kelvin` and `degrees` to `Degree`.

The knowledge layer does not model every concept the application uses. The
concepts that only the app models - document question answering, research
papers and the metadata classes - are listed in `EXTERNAL_CONCEPTS` in
`app/integration/canonical.py` and are covered by the app's fallback ontology
`app/data/ontology.json`. The RDF ontology stays the source of truth for
everything it does model.
