# Graph schema and query behaviour

The knowledge graph is a single RDFLib graph written as Turtle. It combines the
upper ontology, units, domain concepts, tools, providers, capabilities, claims,
and field mappings. Writes are validated with SHACL plus deterministic rule
checks before they are committed, so an invalid candidate never replaces the
current graph.

Code: `src/agent_bazaar/kg/store.py` (write and persistence),
`src/agent_bazaar/kg/queries.py` (queries), `src/agent_bazaar/ontology/shapes.ttl`
and `validator.py` (validation).

## 1. Graph layout

| Subject | Type | Key triples |
| --- | --- | --- |
| `ab:<Concept>` | `owl:Class`, `ab:Concept` | `rdfs:label`, `rdfs:comment`, `rdfs:subClassOf`, `ab:hasDataType`, `ab:unitBearing`, `ab:unitFamily`, `ab:defaultUnit`, `skos:altLabel` |
| `unit:<Unit>` | `ab:Unit` | `ab:unitSymbol`, `ab:unitOfFamily ab:<Family>` |
| `ab:<Family>` | `ab:UnitFamily` | `ab:familyCode`, `rdfs:label` |
| `tool:<tool_id>` | `ab:Tool` | `ab:toolId`, `ab:name`, `ab:description`, `ab:source`, `ab:version`, `ab:hasTrust`, `ab:providedBy`, `ab:hasCapability`, `ab:hasInput`, `ab:hasOutput`, `ab:makesClaim`, `ab:hasFieldMapping` |
| `ab:provider-<provider_id>` | `ab:Provider` | `ab:providerId`, `ab:name` |
| `ab:capability-<slug>` | `ab:Capability` | `rdfs:label`; shared by tools with the same capability |
| `ab:claim-<tool_id>-<index>` | `ab:Claim` | `ab:claimId`, `ab:claimText`, `ab:source` |
| `ab:mapping-<12 hex>` | `ab:Mapping` | `ab:fieldPath`, `ab:direction`, `ab:mapsTo`, `ab:confidence`, `ab:reason`, `ab:status`, `ab:attempts`, `ab:recordedAt`, `ab:recordedBy`, `ab:tool`, optional `ab:unit` |
| `ab:offering-<tool_id>` | `ab:Offering` | `ab:pricingTier`, `ab:accessRequirement`, `ab:priceAmount`, `ab:priceCurrency`, `ab:rateLimit`, `ab:probeBudgetPerMinute`, `ab:ratingValue`, `ab:ratingCount`, `ab:ratingSource`, `ab:docQuality`, `ab:docSubScores`, `ab:mappingCoverage`, `ab:licence`, `ab:termsUrl`, `ab:provenance`, `ab:lastSeen`, `ab:tierEvidence`, `ab:accessEvidence`; linked from the tool with `ab:hasOffering` |

Unit instances live in the `unit:` namespace (`unit:Celsius`), but unit
families live in the ontology namespace (`ab:TemperatureUnit`), because
`units_graph()` builds families with `AB[family_name]` and units with
`unit_iri(local_name)` (`src/agent_bazaar/ontology/units.py:186-199`). A
concept's `ab:unitFamily` and `ab:defaultUnit` therefore point at `ab:...`
and `unit:...` IRIs respectively, and `ab:unitOfFamily` links a `unit:` node
back to an `ab:` family node.

The graph is stored in `data/out/graph.ttl`; the ontology-only artifact is
`data/out/ontology.ttl`. The seed graph artifact was generated by
`scripts/seed_graph.py` from the committed seed specifications and contains
8 tools, 60 concepts, 557 distinct mappings, 0 claims, and about 294 KB of
Turtle.

### Tool and provider nodes

`write_tool()` uses `tool_iri(record.tool_id)` and
`AB["provider-" + record.provider_id]`. It adds the provider's id and name,
the tool's id, name, description, source, version, optional trust, and
`ab:providedBy`. Capabilities are de-duplicated by a slug of the capability text,
so identical capability strings across tools share the same capability node.
Claims use a positional IRI, `ab:claim-<tool_id>-<index>`.

### Inputs, outputs, and mappings

Every mapped field becomes one mapping node. The Tool node points to the
concept through `ab:hasInput` or `ab:hasOutput`, and to the mapping through
`ab:hasFieldMapping` (`store.py:134-190`). Input/output links are concept-level,
not field-level: three inputs mapped to `Latitude` produce one
`ab:hasInput ab:Latitude` triple. The mapping retains the exact field path.

A field mapping owns the confidence, reason, status, attempts, unit, and
provenance. A unit is emitted only when the mapping has one. If the mapped
concept declares a unit family, the graph check requires the unit to belong to
that family; a unit on a non-unit-bearing concept is not rejected by the graph
check, though the Mapper's pre-write rule rejects it.

### Mapping identity and collisions

`KgStore._mapping_iri()` is a deterministic SHA-1 of
`tool_id|field_path|direction`, truncated to 12 hexadecimal characters
(`store.py:109-111`):

```text
ab:mapping-<sha1("open-meteo|output.get:/v1/forecast.body.temperature_2m|output")[:12]>
```

The direction is part of the key, so the same path cannot collide between input
and output. Distinct field paths normally produce distinct nodes. The seed run
reported 512 mapped field results but `describe_graph()` found 557 mapping nodes:
repeated identical mappings (the same tool, field path, and direction) hash to
the same node and collapse. This is expected identity behaviour, not data loss,
but reports must distinguish "mapping results" from "graph mapping nodes".
12 hex characters are not collision-proof in theory; the tool/field set is small
and the digest is deterministic, but a production system should detect or
lengthen the hash.

### Provenance and versioning

Mapping provenance is carried by:

- `ab:confidence` (decimal 0-1);
- `ab:reason` (Mapper's explanation or correction note);
- `ab:status` (string, currently free-form);
- `ab:attempts` (integer, default 0);
- `ab:recordedAt` (UTC dateTime);
- `ab:recordedBy` (string);
- optional `ab:unit`.

`ab:status` and `ab:recordedBy` are plain strings with no SHACL value
constraint, so any writer may set them. The values this repository produces are:

| Value | Set by | Where |
| --- | --- | --- |
| `mapped` | Mapper, initial value when the mapping is built; reaches the graph only if validation passes unchanged | `mapper/agent.py:179` |
| `repaired` | Mapper, after the repair loop succeeds | `mapper/agent.py:319-321` |
| `unmapped` | Mapper, when repair or the graph write failed | `mapper/agent.py:306-311`, `agent.py:349-351` |
| `drift_remapped` | Mapper, after a drift re-map | `mapper/agent.py:504` |
| `updated` | `KgStore.update_mapping` default when no status is supplied | `kg/store.py:244` |
| `mapper` (as `recordedBy`) | Mapper, on a normal mapping | `mapper/agent.py:342` |
| `mapper-drift` (as `recordedBy`) | Mapper, on a drift re-map | `mapper/agent.py:485` |
| `system` (as `recordedBy`) | `KgStore.update_mapping` default | `kg/store.py:245` |

In the committed seed artifact every one of the 557 mapping nodes has
`ab:status "mapped"` and `ab:recordedBy "mapper"`, because the seed run is
offline and every field mapped cleanly on the first proposal.

Known caveat: `write_tool()` adds `ab:recordedAt` directly rather than replacing
it (`store.py:154`). Onboarding calls `map_fields()`, which creates/updates each
mapping via `update_mapping()` with one timestamp, and then calls `write_tool()`,
which adds a second timestamp to the same mapping IRI. All 557 mapping nodes in
the seed artifact therefore have two `ab:recordedAt` values, not two distinct
events. `update_mapping()` itself replaces provenance fields and keeps one
timestamp (`store.py:261`). Timestamped per-write history is not modelled;
`ab:recordedAt` is a mutable property, not an event log.

Tool `ab:version` is the upstream API/spec version, not a graph schema version.
The ontology document declares the upper layer as "frozen at the end of Week 2"
but there is no committed graph migration mechanism. Rebuilding the seed graph
with `scripts/seed_graph.py` is the current reset path.

## 2. Write path and validation

`KgStore` is in-memory. `write_tool` and `update_mapping` follow the same
optimistic candidate pattern:

1. `_candidate()` copies the current graph into a fresh `Graph`, binding the
   standard prefixes.
2. The method adds or replaces triples on the candidate.
3. `_commit()` runs `validate_graph(candidate, shapes)`.
4. On success the candidate becomes the current graph; on failure
   `GraphValidationError` is raised and the current graph is unchanged.

`update_mapping` removes old values with `_replace` for concept, unit,
confidence, reason, status, recordedAt, and recordedBy, then rebuilds all
`ab:hasInput`/`ab:hasOutput` edges for the tool from its mappings
(`store.py:256-263`). It returns `True`; callers get a false/absent
mapping only through lookups.

`GraphValidationError` exposes the full `ValidationResult` as `.result` and
includes up to three violation messages/focus nodes in its string. This is what
`onboard_spec` catches.

`save()` serializes Turtle to the configured graph path (default
`data/out/graph.ttl`) and creates the parent directory. There is no locking,
write-ahead log, or cross-process concurrency control. Do not run two writers
against the same file; the last save wins. Loading is `KgStore.build_default()`,
which starts from upper + units, adds the configured ontology file if present,
and then adds the existing graph file if present
(`store.py:61-90`).

## 3. Query semantics

All public methods are on `KgStore` and return plain dataclasses defined in
`models.py`. Queries operate on the loaded graph only; there is no remote
endpoint.

### `tools_by_capability(capability)`

Matches a capability by:

- exact full IRI;
- exact local name, with or without the `capability-` prefix;
- exact label, case-insensitive;
- slug equality after replacing non-alphanumerics with `-`.

It is not substring, fuzzy, or embedding search. Results are de-duplicated by
tool node and sorted by `(tool_id, iri)`. `ToolSummary.score` is `None` and
`reason` is empty because ranking belongs to the Client.

### `tools_by_io(input_concept, output_concept)`

Uses bidirectional subsumption:

- acceptable inputs = superclass closure of the requested input (a tool that
  accepts an ancestor concept can satisfy a request for a descendant);
- acceptable outputs = descendant closure of the requested output (a tool that
  returns a child of the requested concept is acceptable).

A tool matches if it has at least one acceptable input and at least one
acceptable output. Capabilities are not considered. The closure traverses
`rdfs:subClassOf` in both directions as needed; there is no OWL reasoner.

### `compatible_substitutes(tool_id)`

Returns other tools that share at least one `ab:hasCapability` node and satisfy
both:

- every candidate input accepts every source input (using the upstream
  superclass closure);
- every source output has at least one candidate output in its descendant
  closure.

This implementation is deliberately strict: it compares all candidate/source
input pairs, not only the source's requirements, so a candidate with an extra
input that does not accept one of the source inputs can fail even if its other
inputs are compatible. It excludes the source tool, does not consider trust or
price, and returns summaries sorted by tool id. Client-side substitution adds
trust, evidence, and policy on top of this query.

### `concept_for_field(tool_id, field_path)`

Finds the first mapping, sorted by IRI, whose `ab:fieldPath` and `ab:tool` match,
then returns `str(ab:mapsTo)` or `None`. There is no direction argument; the
canonical field path already contains it. If malformed data contains two
mappings for the same tool/path with different directions, the lexicographically
first IRI wins.

### Concept and tool inspection

- `get_concept(iri)` accepts a full IRI or a local name; returns `None` unless
  the subject is typed `ab:Concept`.
- `ConceptInfo` returns local names for parents, unit family, and default unit;
  missing data type defaults to `"string"` and missing `unitBearing` to `False`.
- `list_concepts()` sorts by local name.
- `list_tools()` returns `ToolSummary` objects with capabilities and provider id.
- `describe_graph()` returns counts of tools, concepts, mappings, and claims.
- `subclass_closure(iri)` returns both ancestors and descendants, including the
  start node; `superclass_closure` and `descendant_closure` are available from
  `kg/queries.py` but are not part of the public store Protocol.

### Commercial and access queries

These helpers read the offering of a tool. They are the graph-side view of the
free-first policy; the policy itself lives in the Client
(`app/agents/ranking_policy.py`).

| Method | Returns |
| --- | --- |
| `tools_by_pricing_tier(tier)` | The tools whose offering declares that pricing tier (`free`, `freemium`, `paid`, `unknown`) |
| `tools_by_access(access_requirement)` | The tools whose offering declares that access requirement (`keyless`, `api_key`, `paid_key`) |
| `executable_tools()` | The tools that may be executed: free and keyless. The licence is only required when the caller asks for it, so a free keyless tool with an unknown licence is included by default |
| `tool_quality_profile(tool_id)` | The `ToolQualityProfile` of one tool: tier, access requirement, price, rate limit, probe budget, rating and its confidence, documentation quality and sub-scores, mapping coverage, licence, terms URL, evidence lists, provenance and the executability flag |
| `candidate_facts(tool_ids)` | The profiles of several tools at once, as a dictionary keyed by tool id |
| `update_tool_quality(tool_id, ...)` | Updates the offering of a tool in one validated write and returns the refreshed profile |

`ToolSummary` carries `pricing_tier`, `access_requirement` and `rating_value`
alongside the identity fields, so a caller that only needs the tier does not
have to build the whole profile.

`update_tool_quality()` accepts `rating_value`, `rating_count`,
`rating_source`, `doc_quality`, `mapping_coverage`, `licence`, `pricing_tier`,
`access_requirement` and `provenance`. It works on a candidate copy of the
graph and commits through the same `_commit()` path as every other write, so an
offering that violates the shapes is rejected and the current graph is left
untouched. Creating an offering for a tool that has none requires
`access_requirement`; without it the call raises `ValueError`.

## 4. Seed counts and what they mean

`data/out/logs/seed_graph.json` records:

```json
{
  "specs": 8,
  "tools_written": 8,
  "mappings": 512,
  "unmapped_fields": 449,
  "graph": {"tools": 8, "concepts": 179, "mappings": 557, "claims": 0},
  "vector_counts": {"ontology_terms": 60}
}
```

`mappings` is the number of `FieldMapping` results the Mapper produced across the
two directions; `graph.mappings` is the number of distinct mapping IRIs. The
unmapped count is the remainder after mapping 8 specs, not a percentage and not a
coverage claim for the full 98-spec corpus. `seed_graph.json` only reports the
ontology-term count; the script also indexes tool descriptions and corrections.
A separate `VectorService` count on the current persisted index reports 60 ontology
terms, 8 tool descriptions, and 0 corrections.

## 5. Operational checks

```powershell
python scripts/seed_graph.py
python -c "from agent_bazaar.kg.store import KgStore; s=KgStore.build_default(); print(s.describe_graph()); print(s.validate().conforms)"
python -m pytest tests/test_kg_store.py tests/test_kg_queries.py
```

Rebuild order matters: build the ontology before the graph, because
`KgStore.build_default()` loads the ontology file before the graph file. The seed
script does this in one run. After a shape change, re-run `validate()`; after a
corpus change, rebuild and compare both mapping-result and distinct-node counts.

## 6. Name mapping in the application layer

The application layer keeps its own vocabulary, so the RDF graph is read through
`app/integration/canonical.py`, the single translation point between the two
layers. The concept names of the app are mapped onto the canonical ones
(`LocationName` to `PlaceName`, `CityName` to `City`, `Coordinates` to
`Position`, `Money` to `MoneyAmount`, `Text` to `Description`, `Number` to
`Count`, `DateTimeISO` to `DateTime`) and the unit names likewise (`C` to
`Celsius`, `F` to `Fahrenheit`, `K` to `Kelvin`, `degrees` to `Degree`).
`app/integration/graph_adapter.py` applies that mapping when it serves the
graph to the Client.

The concepts the knowledge layer does not model yet - document question
answering, research papers and the metadata classes - are listed in
`EXTERNAL_CONCEPTS` and are covered by the app's fallback ontology
`app/data/ontology.json`.

## 7. Offering nodes: commercial, access and documentation facts

The commercial, access, reputation and documentation facts of a tool live on one
`ab:Offering` node per tool, reached from the tool with `ab:hasOffering`.

### 7.1 Status of the extension

This is a **versioned upper-level extension added after the Week 3 ontology
freeze**. The frozen 60-concept domain layer and the minimum shape set are
unchanged; the extension adds one class, one object property, eighteen datatype
properties and two shapes to the upper layer. `src/agent_bazaar/ontology/upper.ttl`
carries the note in a comment above the offering section, and the ontology
artifacts are extended rather than rewritten, so the existing evaluation stays
valid.

There is still no committed graph migration mechanism. Rebuilding the graph with
`scripts/seed_graph.py` remains the reset path.

### 7.2 The node

| Property | Range | Meaning |
| --- | --- | --- |
| `ab:hasOffering` | `ab:Offering` | From the tool to its offering. A tool has **at most one** offering |
| `ab:pricingTier` | string | `free`, `freemium`, `paid` or `unknown`. Absence of evidence is never `free` |
| `ab:accessRequirement` | string | `keyless`, `api_key` or `paid_key` |
| `ab:priceAmount` | `xsd:decimal` | The published price, when the document states one |
| `ab:priceCurrency` | string | ISO 4217 code of the price |
| `ab:rateLimit` | string | The published limit, in words |
| `ab:probeBudgetPerMinute` | `xsd:integer` | Requests per minute this project may send |
| `ab:ratingValue` | `xsd:decimal` | The shrunk developer rating, between 0 and 1 |
| `ab:ratingCount` | `xsd:integer` | The number of reviews behind the rating |
| `ab:ratingSource` | string | Where the rating came from |
| `ab:docQuality` | `xsd:decimal` | The reproducible documentation quality, between 0 and 1 |
| `ab:docSubScores` | string | JSON object of the seven documentation sub-scores |
| `ab:mappingCoverage` | `xsd:decimal` | The share of the listing's fields the Mapper typed, between 0 and 1 |
| `ab:licence` | string | The declared licence of the API or its data |
| `ab:termsUrl` | string | The provider's terms or licence page |
| `ab:provenance` | string | JSON record of how the facts were obtained and reviewed |
| `ab:lastSeen` | `xsd:dateTime` | When the facts were last written |
| `ab:tierEvidence` | string | The matched pricing fragments, joined with a pipe character |
| `ab:accessEvidence` | string | The matched access signals, joined with a pipe character |

The offering IRI is deterministic: `ab:offering-<tool_id>`, built by
`kg.quality.offering_iri()`. A tool without an established access requirement
keeps **no** offering node at all, so the graph never asserts a commercial fact
that was not established.

### 7.3 The shapes

`ab:OfferingShape` (`sh:targetClass ab:Offering`):

| Path | Constraint |
| --- | --- |
| `ab:pricingTier` | Exactly one, of type `xsd:string`, in (`free`, `freemium`, `paid`, `unknown`) |
| `ab:accessRequirement` | Exactly one, of type `xsd:string`, in (`keyless`, `api_key`, `paid_key`, `unknown`) |
| `ab:ratingValue` | At most one, `xsd:decimal`, between 0 and 1 |
| `ab:ratingCount` | At most one, `xsd:integer`, at least 0 |
| `ab:docQuality` | At most one, `xsd:decimal`, between 0 and 1 |
| `ab:mappingCoverage` | At most one, `xsd:decimal`, between 0 and 1 |
| `ab:probeBudgetPerMinute` | At most one, `xsd:integer`, at least 1 |

`ab:ToolOfferingShape` (`sh:targetClass ab:Tool`):

| Path | Constraint |
| --- | --- |
| `ab:hasOffering` | At most one, and the value must be an IRI |

The remaining predicates are free strings; they carry no value constraint, so
any writer may set them. The values this repository produces are listed in
Section 7.2.

### 7.4 Turtle example

The example below is the real output of `kg.quality.offering_triples()` for a
free, keyless tool with a licence, a terms page, a rate limit and a probe
budget:

```turtle
@prefix ab: <https://agent-bazaar.local/ontology#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

<https://agent-bazaar.local/tool/example-tool> a ab:Tool ;
    ab:hasOffering ab:offering-example-tool .

ab:offering-example-tool a ab:Offering ;
    ab:accessEvidence "no security scheme, credential parameter or platform rule matched" ;
    ab:accessRequirement "keyless" ;
    ab:docQuality 0.8125 ;
    ab:docSubScores "{\"breadth\": 1.0, \"description\": 0.5, \"examples\": 0.0, \"field_descriptions\": 1.0, \"not_deprecated\": 1.0, \"response_schemas\": 1.0, \"typed_io\": 1.0}" ;
    ab:lastSeen "2026-10-21T09:30:00+00:00"^^xsd:dateTime ;
    ab:licence "CC-BY-4.0" ;
    ab:mappingCoverage 0.9 ;
    ab:priceAmount 0.0 ;
    ab:pricingTier "free" ;
    ab:probeBudgetPerMinute 60 ;
    ab:provenance "{\"method\": \"deterministic_rules\", \"source\": \"openapi_document\"}" ;
    ab:rateLimit "600 calls per minute, 5000 per hour" ;
    ab:termsUrl "https://example.org/terms" ;
    ab:tierEvidence "free tier" .
```

The rating triples are written together with the rating value: a rating always
carries its count, and the source is written when it is known.

### 7.5 Derived values

Two values are computed from the graph rather than stored:

- **Rating shrinkage.** `kg.quality.shrunk_rating(sum, count)` returns
  `(sum + 0.5 * 2) / (count + 2)` and a confidence of `count / (count + 2)`.
  With no ratings at all it returns the prior mean 0.5 and a confidence of 0.
  The store does not apply it on its own: the caller computes the shrunk value
  and passes it to `update_tool_quality(rating_value=..., rating_count=...,
  rating_source=...)`.
- **Mapping coverage.** `kg.quality.mapping_coverage(graph, tool_id)` is the
  share of the tool's mappings that the Mapper typed successfully
  (status `mapped`, `repaired` or `drift_remapped`), multiplied by
  `0.5 + 0.5 * mean confidence`. The onboarding path computes the same number
  from the mapping result, because the unmapped fields are never written to the
  graph.

`ToolQualityProfile.is_executable` is true when the tier is `free` and the
access requirement is `keyless`. A known licence is only required when the
caller asks for it, which is the same default the Client policy uses
(`AB_REQUIRE_KNOWN_LICENCE=false`).
